# 0016. Releases: release-please tags, dist builds

- Status: accepted
- Date: 2026-10-29

## Context

The project had no releases: no tags, no changelog, and `.project-standards.yaml` recorded
release-please as skipped because nothing was published. The owner wants an installable
`shoreline-recon` binary (GitHub Releases, a shell installer and Homebrew) with versions and
changelogs derived from the conventional commits already in use. The repository is public.

Two tools cover this. release-please opens a release PR from conventional commits and, when it
is merged, tags `vX.Y.Z` and creates the GitHub Release. dist (cargo-dist) builds the binaries
from a tag and generates the installers and a Homebrew formula. Both create GitHub Releases by
default, and a tag or release made with the workflow's default `GITHUB_TOKEN` starts no other
workflow.

## Decision

Decided by the project owner on 2026-10-29:

1. release-please owns versions, tags, `CHANGELOG.md` and the GitHub Release
   (`release-please-config.json`, `.release-please-manifest.json`,
   `.github/workflows/release-please.yml`), as in the owner's other repositories: release type
   `simple`, the version in `[workspace.package]` of `Cargo.toml` marked
   `# x-release-please-version`, tags without a component (`v0.1.0`). The manifest starts at
   `0.0.0` so the first release is `0.1.0`.
2. release-please runs with a GitHub App token (`vars.RELEASE_PLEASE_APP_ID`,
   `secrets.RELEASE_PLEASE_PRIVATE_KEY`), so its tag starts `release.yml`. The same workflow
   syncs `Cargo.lock` into the release PR, because CI builds with `--locked`.
3. dist 0.32.0 builds `shoreline-recon` on the tag for `aarch64-apple-darwin` and
   `x86_64-unknown-linux-gnu`, with the shell and Homebrew installers. `create-release = false`:
   dist uploads to the release that release-please created. `release.yml` is generated by
   `dist generate` from `dist-workspace.toml` and not edited by hand; its actions are pinned to
   commits through `[dist.github-action-commits]`.
4. The Homebrew formula is published to `laurigates/homebrew-tap` with
   `secrets.HOMEBREW_TAP_TOKEN`.

## Consequences

- Versions, tags and `CHANGELOG.md` change only through the release PR. PR titles and squash
  commit subjects must be conventional commits; a fenced code block in a squash commit body can
  stop release-please from parsing the range.
- The repository needs the App installed (gitops `release_please = true`), the
  `HOMEBREW_TAP_TOKEN` secret, and the `laurigates/homebrew-tap` repository.
- The formula installs only the binary. External tools (ffmpeg, COLMAP, OpenMVS, Brush, the
  segmentation model and renderer) are not dependencies of it; dist adds Homebrew dependencies
  only for linked libraries. They come with the local tool profile and the tap formulas.
- Until the binary embeds its defaults, it reads `defaults.toml` and `tools.toml` from beside the
  dataset config, so a release is used from a checkout of the repository's `configs/`.
- `release.yml` also runs `dist plan` on every pull request, which checks that the release
  configuration still builds a plan.
